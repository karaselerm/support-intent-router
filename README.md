# Support Intent Router

Система классификации и маршрутизации англоязычных обращений в банковскую поддержку.
Определяет тему сообщения и предлагает очередь обработки. При низкой уверенности
модели обращение передаётся на ручную сортировку; оператор может подтвердить
или исправить предложенную тему.

**Статус:** проектирование MVP. В репозитории подготовлены дизайн системы и настройки
окружения разработки. Обучение модели, API и интеграция с поддержкой запланированы.

## Цель проекта

Сократить время первичной сортировки обращений и количество повторных переводов
между очередями поддержки. Целевой бизнес-результат — снижение среднего активного
времени сортировки минимум на 20% относительно ручного процесса.
Этот эффект необходимо подтвердить в пилоте на реальном потоке обращений.

## Ожидаемый результат

MVP, который:

- определяет одну из 77 тем банковского обращения;
- возвращает тему, оценку уверенности и предлагаемую очередь обработки;
- передаёт неоднозначные обращения на ручную сортировку;
- позволяет оператору подтвердить или исправить тему;
- сохраняет ручной процесс обработки при недоступности модели.

Для первой версии планируется локальный API и проверка маршрутизации
на демонстрационных очередях. Подключение к реальной поддержке потребует
согласования справочника очередей и правил обработки критичных обращений.

## Подход

Вход модели — текст одного обращения на английском языке. Например:
`Is there a way to know when my card will arrive?` → `card_arrival`.
Пример взят из описания датасета PolyAI.

Baseline строится на TF-IDF слов и логистической регрессии. Кандидат MVP дополняет
словесные признаки символьными n-граммами для проверки устойчивости к опечаткам
и вариантам написания. Выбор модели определяется качеством и затратами ресурсов.
Порог уверенности подбирается на отдельной валидационной выборке.

Предварительные критерии качества MVP:

| Метрика | Цель |
| --- | --- |
| Macro-F1 по 77 темам | ≥ 0,85 |
| Точность автоматически принятых решений | ≥ 0,95 |
| Доля обращений, принимаемых автоматически | ≥ 0,50 при выполнении требования к точности |

Это целевые значения, которые предстоит проверить экспериментально.
Подробные правила сравнения с baseline, разбиения данных и выбора порога
описаны в [дизайн-документе](docs/ml_system_design_doc.md).

## Данные

Для разработки выбран [BANKING77 от PolyAI](https://github.com/PolyAI-LDN/task-specific-datasets):
10 003 обучающих и 3 080 тестовых примеров, 77 категорий банковских обращений.
Язык — английский, лицензия — CC BY 4.0.
Дополнительное описание: [карточка датасета](https://huggingface.co/datasets/PolyAI/banking77).

Данные не включены в репозиторий. При загрузке необходимо зафиксировать версию
источника и контрольные суммы файлов. BANKING77 позволяет оценить классификацию,
но не содержит реальных очередей поддержки и времени обработки обращений.
Для оценки бизнес-эффекта потребуются данные пилота.

Работа авторов: Casanueva et al. (2020),
[Efficient Intent Detection with Dual Sentence Encoders](https://arxiv.org/abs/2003.04807).

## Окружение разработки

Требуются Python 3.11–3.13, Git и [uv](https://docs.astral.sh/uv/getting-started/installation/).
Все команды выполняются из корня репозитория.

```bash
uv sync --frozen
```

Версии зависимостей закреплены в `uv.lock`. Сейчас окружение содержит инструменты
качества кода; библиотеки для обучения будут добавлены вместе с ML-пайплайном.

### Линтер и форматер

Проверка кода и форматирования:

```bash
uv run --frozen ruff check .
uv run --frozen ruff format --check .
```

Автоматическое исправление и форматирование:

```bash
uv run --frozen ruff check --fix .
uv run --frozen ruff format .
```

### Pre-commit

Установка проверок перед коммитом:

```bash
uv run --frozen pre-commit install
```

Запуск проверок для всех отслеживаемых файлов:

```bash
uv run --frozen pre-commit run --all-files
```

Для проверки файлов, ещё не добавленных в Git:

```bash
uv run --frozen pre-commit run --files README.md pyproject.toml uv.lock .pre-commit-config.yaml .gitignore docs/ml_system_design_doc.md
```

Хуки запускают Ruff, проверяют YAML/TOML, пробелы в конце строк,
завершающую новую строку и размер файлов. Используются версии из `uv.lock`;
`uv` должен быть доступен в PATH, в том числе при коммите из IDE.
После автоматических исправлений нужно проверить изменения и повторно добавить
исправленные файлы в индекс Git.

## План развития

1. Подготовить данные, проверить дубликаты и распределение классов.
2. Обучить baseline и оценить его на фиксированных выборках.
3. Сравнить модели и выбрать порог передачи на ручную сортировку.
4. Реализовать API, проверить задержку, нагрузку и обработку сбоев.
5. Провести теневой пилот, затем оценить влияние системы на работу поддержки.
